01

Who can do what

Five roles, two kinds of customer. A broker's staff come in three grades, an employer's in two. Pick a role to see what it can do; the right-hand note on each row is the line of code that decides it, so none of this is a policy document that can drift from the product.

Two things catch people out. A broker's non-admin staff can read endorsement jobs but cannot upload one; an employer's non-admin staff can upload but cannot decide (proceed, retry, cancel or close). And every read is also scoped to the caller's own tenant: a broker only ever sees its own employers, an employer only its own policies, whatever the role.

02

How the services talk

Services never reach into each other's databases. When something happens, the owner records an event alongside the change (an outbox), a relay publishes it, and whoever cares reads it. That is why a policy approval opens a deposit account without the policy service knowing billing exists. Click a topic to see who writes it and who reads it.

04

Why nothing is exposed

The core services have no public face. Three independent checks sit between the internet and a rate card or an employee list, and each one fails closed.

What the gateway adds

  • Sign-in is the only door. The portal keeps the token server-side in an encrypted session; the browser only holds a session cookie, never a token it could leak.
  • Contract, not pass-through. A request that is not in the contract is a 404. A field that is not on the allow-list never reaches a service.
  • Tenant from the token. An employer's id comes from who it is, never from a URL a user could edit.

What every service checks again

  • A shared gateway secret and a key derived from the session must accompany each call, or the service refuses it. A request that skips the gateway is refused at the first line.
  • The role, per route. Each service re-checks the role itself; it does not trust that the gateway already did.
  • The tenant, per row. Queries are scoped to the broker or employer in the token, so a valid user cannot ask for someone else's data.

Local development can run with the secret left blank, which switches the check off so tools can be tried without ceremony. Production sets it; the setup guide in the repository says how.

What is not built

A reference that only lists what works is a brochure. These are the gaps, as of the code this page was generated from.

Needs a contract before it can exist

  • Live connections to individual TPAs and insurers. The lifecycle states and the endpoint that drives them are built; the adapters that talk to each TPA and insurer are not, because each needs credentials and a signed agreement.
  • E-card and endorsement-copy retrieval, which come from the TPA or insurer.
  • SMS, WhatsApp and one-time passwords. These need a telecom sender registration.
  • Payments. The deposit ledger records money received; it does not collect it.

Ours to build next

  • Refusing an upload for an employee whose enrollment window has closed. The check exists and can be called; wiring it into validation needs a decision on whether a closed window blocks or only warns.
  • Deposit accounts that fund a company or a group of policies in the legacy way, and parent and child employers.
  • Port the premium types production actually uses; some legacy types map only approximately.
  • A decision on the leaving day for removals, and on the default refund when pro-rata is off.
